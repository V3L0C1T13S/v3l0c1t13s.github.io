Rosemary is a compatibility layer we're working on for running macOS applications on Linux. It's still called Rosetta 3 internally, though we're working on changing that; Rosemary is the name we plan to use when we release it. It's important to establish as well that when we say "Rosetta 3" in this blogpost, we are referring to the name of our hobby project before turning it into Rosemary, it has no affiliation with Apple's official Rosetta technology or any other Apple product, and diverges from it in plenty of ways including overall design. It started as a toy Rosetta 2 remake. Now we're running Mac applications through our own frameworks and translating Metal to Vulkan. Things got a little out of hand!

## A Rosetta 2 remake

Originally, this was a toy project with a fairly specific ambition: build our own equivalent of Apple's Rosetta 2, so Intel Mac applications could keep running on Apple silicon after Apple's translation layer went away. Apple has described general-purpose Rosetta availability as extending [through macOS 27](https://developer.apple.com/documentation/apple-silicon/about-the-rosetta-translation-environment). Despite that, software doesn't stop being useful just because the transition it was written before is considered finished.

The initial challenge was already plenty ambitious: take an x86-64 macOS executable and run it on an AArch64 Mac. Linux wasn't part of that first goal. We had an entire CPU boundary to get across first.

Luckily, we had a place to start: Microlift, our binary lifter. It takes machine instructions and expresses their behavior in Cranelift's intermediate representation, which can then be compiled into code for the host CPU. For Rosetta 3, that meant taking Intel code and producing code an Apple silicon Mac could execute.

Using a compiler IR gives us room to optimize the translated program. For example, x86 instructions often update CPU flags that subsequent instructions never read. Representing those flags explicitly lets the compiler eliminate unused calculations. It also has a cost: lifting and compiling code takes time. This is our own approach to the problem, and calling the original project a Rosetta 2 remake describes its purpose rather than an identical implementation.

Of course, getting the CPU instructions right is only the beginning. An application would quite like its libraries, threads, and operating system calls to work too. Microlift handles the instructions; building the environment around them was Rosetta 3's job.

## Loading and running Mac apps

Rosetta 3's history starts on July 30 with `machish`, our Mach-O loader. Mach-O is the executable format macOS uses. Over the next few days, the runtime gained the ability to link images, execute Intel code through Microlift, call host functions, and handle thread-local storage, signals, and unwinding. Then came Objective-C metadata, classes, and message dispatch. Then, not long after on August 1st, we got to write a short, but utterly satisfying commit message: "DELTARUNE runs"

An actual game! Suddenly all that loading, binary lifting, and runtime work had something much more fun to show for it.

That was an early macOS milestone. Getting an application to run there still meant we had an actual macOS installation supplying the frameworks underneath it.

## Bridging host libraries

One of the earliest and most influential decisions we made was to bridge guest API calls to their native ARM equivalents. When translated Intel code calls a function exported by a system library, we can generate specialized code to call it directly rather than synchronize the register state and ask a dispatcher for assistance.

The tricky part is that different architectures have different rules/layouts for passing arguments and returning values, known as an [Application Binary Interface](https://en.wikipedia.org/wiki/Application_binary_interface). A function returning a structure, a function accepting variable arguments, and an Objective-C method can all need different handling. Calls also go both ways: a host framework might call back into the application's translated code. The runtime has to make that round trip work.

This meant Rosetta 3 was already doing much more than recompiling instructions. It understood how to load a Mac application and its relationship with the libraries around it.

## Fast import calls

Calling a native library saves us from translating its implementation, but crossing into it can still be expensive. If every little library call means saving the emulated CPU state, returning to the VM's dispatch loop, figuring out how to call the host function, and then resuming translated code, we've put quite a toll booth in front of that native code. Microlift's fast import calls let us remove that detour for calls we understand.

The integration starts with the loader and Rosetta 3's ABI tables. The loader tells us which function an import resolves to; the tables describe its arguments, return value, and whether it needs special handling. For an eligible import, Rosetta 3 gives Microlift the import's guest address, the native function's address, its signature, and the guest calling convention. We explicitly check that the resolved target isn't still guest code. Jumping straight into Intel instructions on an ARM CPU would be a rather short-lived optimization.

When Microlift lifts a call to that import, it emits a typed Cranelift call inside the translated region. It takes the arguments from the values representing the guest's registers, or from the guest stack where the calling convention requires it. Cranelift then places those values where the host ABI expects them. After the native function returns, its result becomes the appropriate guest register value, and execution continues in the translated code. The library function itself remains a separate function; it's the calling sequence we're compiling into the region.

That means no VM exit for the supported call, and no full guest-register-state save and reload around it. Cranelift still has to preserve values across a normal native call, but it can manage those values as part of the surrounding compiled code. For something like `strlen`, the translated caller can pass its pointer to the native implementation and use the returned length directly. The less work the library function does, the more the cost of reaching it matters.

It's useful to compare this with [FEX's documented library thunking approach](https://github.com/FEX-Emu/FEX/blob/main/ThunkLibs/README.md). FEX also calls native libraries and supports callbacks. Its traditional thunk libraries use a guest-side packer to put arguments into a structure on the guest stack, a special thunk operation to cross into host code, and a host-side unpacker to call the implementation and write back the result. That requires matching guest and host thunk libraries. Our eligible fast calls avoid that intermediate argument structure and pack/unpack sequence: the compiler already knows the signature and generates the ABI conversion at the call site.

The flexibility comes from making this a capability of the lifter. Each import describes the guest and host conventions separately; Microlift can even mix guest calling conventions within one translated region. Rosetta 3 uses that machinery to target native library functions, and selected Objective-C runtime operations can instead target typed wrappers that translate class identities. We can keep necessary compatibility work while still avoiding the VM dispatch loop. Adding an ordinary compatible import means describing its signature and resolving its target, without building a replacement guest library just to carry the arguments across.

There are deliberate limits. Variadic calls, functions taking guest callbacks, and signatures or shims that cannot use this path stay on the slower runtime path. A fast callee must not re-enter guest code against the current register context: publishing selected pinned registers isn't the same as synchronizing the full guest state. This is also why the Objective-C fast path is restricted to selected operations that cannot dispatch a guest method. Fast imports give us less work at supported call boundaries, not automatic compatibility with every ABI or a measured claim that Rosemary outperforms FEX overall.

And here's where things got interesting: the loader and library bridges were useful even when there was nothing to recompile.

## Making the leap to Linux

On August 19, execution was split into native and emulated backends. The emulated backend runs x86-64 code through Microlift. The native backend runs a Mach-O slice matching the host CPU directly, while keeping the loader and runtime around it. Support for x86-64 hosts followed on August 22.

This opened up a much bigger possibility. An Intel Mac application on an Intel Linux machine already speaks the CPU's instruction set. What it lacks is the operating system environment it was built for. It still needs a Mach-O loader, Darwin behavior, and macOS libraries. Recompiling its instructions wouldn't provide any of those things.

By August 27, we had an initial Linux port. Now we had to give those Mac applications something to talk to! At that point, calls that could previously go to macOS needed somewhere else to go. The Darwin shim became the place to handle those differences: use the host's facilities where they fit, and translate the behavior where they don't.

Both systems have familiar functions for files, sockets, and threads, but familiar names can hide incompatible details. Error numbers, structure layouts, file-opening flags, directory entries, and thread-local storage all need care. If we pass a Darwin flag straight to Linux and it means something different there, we've successfully called the wrong thing. Likewise, if a seemingly standard structure differs between the Darwin ABI and Linux in even the tiniest way, a guest application reads the wrong data and could go down a completely different path that leads to a segmentation fault nearby the call site in the best case; Yes, a segfault with an obvious cause is actually considered the BEST scenario here, with the worse ones being obscure DNS lookup issues, files failing to open, or even the app thinking a plain file is a socket it should call `send()` on (that actually happened, by the way). That's a particularly annoying kind of progress. The application needs the exact semantics of the behavior it asked for.

## Building the frameworks

The work quickly extended above that layer. A custom Objective-C runtime arrived with the initial Linux port, followed by implementations of CoreFoundation, Foundation, libdispatch, and AppKit. These supply things applications expect to exist: objects and strings, collections, notifications, work queues, windows, views, and events. CoreAudio and IOKit work brought audio and device support into the picture, with SDL3 providing portable facilities for parts of the windowing, input, and audio stack.

## Metal to Vulkan

And then we got to Metal. Yes, we're translating GPU work now too. We now have an initial Vulkan-backed Metal runtime and shader translation work that produces SPIR-V, along with implementations for compute dispatch, render passes, and presentation. The CPU translator now has some company: a graphics API implementation and a shader translator. That's quite a detour from our original toy project.

## Running Intel macOS apps on an AArch64 Linux host

By now I can hear you asking: "If Rosemary started out as a layer for running Intel macOS apps on an AArch64 macOS host, does that technology still work on Linux?" And the answer is: yes! Absolutely, and it does! Earlier we discussed how Rosemary draws explicit boundaries between what is host code and what is guest code, and how we developed an execution context abstraction to support this. Thanks to our careful design choices, Rosemary can run Intel macOS apps on AArch64 Linux systems without any external tooling, unlike how it's been with WINE/Proton for a long time.

Because of how integrated and fundamental the emulation side of Rosemary is with the rest of it, we generally manage to outperform traditional emulation that involes running the whole compatibility layer under emulation. Unlike running WINE through FEX, all of the Darwin translation code will run through your host AArch64 system transparently using the fast import system we discussed above. This means that your CPU doesn't waste time emulating the semantics of something it literally has a readily compiled host version for, it just executes the host version and skips the overhead entirely.

## What comes next

There's still a lot to do. Rosemary is experimental, application coverage is incomplete, and we're still filling in frameworks and working on performance. The demo is exciting, but it isn't a promise that every Mac application will work. The CPU translation path currently uses JIT compilation; ahead-of-time recompilation is still a future goal. Having an implementation of an API, or getting one application past a failure, doesn't mean everything using that API now works.

But the project has acquired a much bigger purpose. The original goal was to keep Intel Mac software running across a CPU transition. Now we're also working to let Mac software run across an operating system boundary, sharing the same loader, runtime, and framework implementations whether the application's instructions need translation or can execute directly.

That's why we're planning to call it Rosemary. Rosetta 3 was a fitting name when we were trying to keep Intel Mac apps alive on Apple silicon. Now we're building toward a future where those applications can live on Linux too.

For something that started as a toy project, I'd say that's a pretty cool place to end up.
